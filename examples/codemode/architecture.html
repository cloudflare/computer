codemode example — system architecture

One Workspace, three backends, and an optional agent layer on top.

PREVIEW ONLY — APIs are unstable and the design is subject to change.

The core idea

A Workspace is a filesystem plus a set of interchangeable backends. Each backend is a different way to run a command against the same files. This example registers three of them and lets an LLM choose which one runs each command — while keeping the workspace itself completely unaware that a model exists.

Two principles drive the design: one Durable Object owns the filesystem, and agency is an opt-in layer, never baked into the workspace.

Layers

layer 1 The workspace (no model)

The CodemodeExample Durable Object constructs a Workspace over its own ctx.storage and registers three backends. It exposes deterministic routes — PUT/GET /file and POST /exec — and a getWorkspace() stub. Nothing here mentions an LLM. A workspace used this way is never agentic.

layer 2 The agent (opt-in)

POST /agent runs a model loop in the Worker, reaching the workspace through its stub. It builds an exec tool whose backend parameter is an enum; the model picks per call. The workspace has zero dependency on this layer. For long runs, the loop would move to its own Durable Object holding a stub.

layer 3 Approval (human in the loop)

Commands the policy holds back — every write, and everything on container — do not run. The turn stops with a pending approval and resumes on POST /approvals/<id>. That wait outlives the request, so the paused turn lives in a second Durable Object, AgentSession, which holds no workspace stub and cannot itself run anything.

The three backends

A backend adapter is registered inside the Durable Object, but the place a command actually runs is separate. All three reach back to the one filesystem.

BackendCommand is…Runs inReaches the fs viaBoot cost
shell a shell line Dynamic Worker (just-bash) WorkspaceServiceProxy loopback → DO isolate cold start
codemode JavaScript Dynamic Worker (JS sandbox) state.* RPC dispatchers → DO isolate cold start
container a shell line Cloudflare Container (wsd) filesystem sync over capnweb → DO container boot (first use only)

Backends connect lazily: a backend is dialed on its first exec and the handle is cached. Registering the container costs nothing until a command routes to it — and never if the model never picks it.

How codemode reaches the filesystem

The codemode backend runs an LLM-authored snippet in an isolated Dynamic Worker with globalOutbound: null, so it has no path to the public internet. Its only door to the outside is the state.* namespace the backend injects: 

await state.mkdir("/workspace", { recursive: true });
await state.writeFile("/workspace/hello.txt", "hello world");
return await state.readFile("/workspace/hello.txt");   // → stdout

Each state.* call dispatches over Workers RPC to functions defined in the Durable Object, which forward straight to the live WorkspaceFilesystem. The snippet's return value and console.log output become stdout; a thrown error becomes stderr with exit code 1.

The namespace mirrors the filesystem surface the shell backend reaches — reads (readFile, readFileBytes, stat, lstat, exists, readlink, readdir, find, ls, grep) and mutations (writeFile, mkdir, rm, chmod, symlink). The only operation left out is the streaming readFile variant, since a ReadableStream cannot cross the sandbox boundary; readFileBytes returns a Uint8Array instead.

The one subtlety worth internalising: decideApproval() runs twice — once to gate, once on replay. The AI SDK re-checks the policy when a turn resumes and converts an approved call into a denial if the answer changed. That is why the policy is a pure function of the command and the backend, with no clock and no mutable state: anything else would make approvals decay on their own.

The approval route

Where every branch goes, and what the client gets back. The two entry points funnel into one model loop, and the loop can come back around: answering an approval resumes the turn, and the resumed pass may stop on a different command.

Why 404 and 202 are different answers

404 means the id is not waiting for an answer — either it was never issued, or somebody already answered it. Both are the same fact, and both have to reject: treating a repeat as a fresh approval would run the command a second time. 202 means the answer was recorded but the turn is still waiting on others, because one model step can propose several commands and the resume has to carry every answer at once. Only the last answer resumes the turn, which is why the reply to POST /approvals/<id> is sometimes a transcript and sometimes a receipt.

Request flows

Deterministic — POST /exec

  1. Client posts { command, backend }.
  2. Worker calls stub.getWorkspace(), then ws.shell.exec(command, { backend }).
  3. The Workspace routes to the named backend (or the default, shell).
  4. The backend runs the command; file ops land in the DO's store.
  5. Worker returns { exitCode, stdout, stderr }.

Agentic — POST /agent

  1. Client posts { prompt }.
  2. Worker builds the model + exec tool over the workspace stub.
  3. The model emits an exec tool call, choosing a backend.
  4. The tool runs it; the model reads the result and continues.
  5. On stop, Worker returns the transcript with toolCalls[].backend.

Gated — POST /approvals/<id>

  1. The policy holds a command back, so the tool never executes it.
  2. The turn returns awaiting-approval; Worker stores its history in AgentSession.
  3. A human reads GET /approvals and answers one entry.
  4. On the last answer, Worker replays the stored history with a tool-approval-response attached.
  5. The approved command runs for real; a denied one comes back to the model as execution-denied.
